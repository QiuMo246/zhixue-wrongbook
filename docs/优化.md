## P0 · 确定性故障

### 1. `zx_sync_browser` 每次调用必然 TypeError 崩溃（已运行时验证）

- 位置：`server.py:705`（调用点）、`server.py:129`（定义）
- 现象：`sync_captured(store, cap, images_dir=_abs_images(), ...)` —— `_abs_images(paths)` 是**必传参数**，零参调用直接抛
  `TypeError: missing 1 required positional argument: 'paths'`。
- 后果：CDP 采集就算成功抓到数据，也会在入库前一步崩掉。与"真机联调未完成（not_verified）"的标注吻合——**这个工具从写下那天起就没跑通过一次**。
- 修法：改成 `images_dir=CONFIG.path("images_dir")`。

## P1 · 门禁漏洞与"静默没做"类

### 2. 包六"weak 不许冒充 strong"门禁可被自报字段绕过

- 位置：`practice_gates.py:117-150`（`gate_export_items`）、`practice_gates.py:75,110`（strength 误标）
- 问题：门禁对条目自带的 `strength` **照单全收**——宿主只要在 items 里写
  `verified=True, strength="numeric"`，不调任何验证就能过闸。
- 更糟：`zx_practice_verify` 在验证**失败**时也返回 `strength="numeric"`：
  - `:75` 回代不成立 → `strength=STRENGTH_NUMERIC`
  - `:110` 数值不等 → `strength=STRENGTH_NUMERIC`
  即**一次真实的验证失败产出的令牌，恰恰能解锁这道门禁**。
- 【二轮补充】`mcp_e2e.py` 的出卷正例恰好也传了自报 `strength: "exact"`（`mcp_e2e.py:358`），
  所以现有验收**测不出**这个洞——金丝雀自己沾着问题过闸。
- 对比：self_check 路径是门禁内当场重算的（诚实）；strength 路径却是纯荣誉制。
- 修法（二选一）：门禁内对声称强验证的条目**重跑** `verify_answer(answer, standard_answer, self_check)`，
  不要信任传入的 strength；或 `zx_practice_verify` 通过时在 server 进程内记 `gen_id → strength` 收据，
  导出时核对收据。前者改动小，但要求导出条目带回 standard_answer/self_check 原料。

### 3. `zx_sync(exam_ids=...)` 配默认 `max_exams=5` 会静默同步 0 道题

- 位置：`zhixuewang.py:387-389`
- 链路：`zx_list_exams` 默认列 20 场 → 用户选了第 8 场 → `zx_sync` 先 `list_exams(limit=max_exams=5)` 截断，**再**按 exam_ids 过滤 → 目标考试被截掉。
- 后果：`exams_scanned: 0` 但 `ok=true`，宿主很可能报"同步完成"。这正是 README 里点名最危险的一类失败："不报错，结果是错的"。
- 修法：传了 exam_ids 时不截断；或对"exam_ids 全部落空"显式报错。

### 4. `get_questions(needs_review=true)` 会少报

- 位置：`store.py:530-537`
- 问题：SQL 里先 `LIMIT`，`needs_review` 过滤在 Python 里**之后**做。若最近 20 题里只有 5 题带复核标记，就只返回 5 道——尽管第 21 道往后还有。
- 后果：复核队列是"人工兜底"用的，少报恰恰漏掉最需要看的题。
- 修法：条件下推到 SQL（`json_extract(analysis,'$.needs_review')`），或先查指纹再取行。

### 5. `eval_expr` 大指数无界消耗（两轮独立实测，结论一致）

- 位置：`practice_gates.py:37-57`
- 问题：`self_check` 是宿主可控输入，表达式里 `**` 不设防。白名单 `fullmatch` 只锁字符集，没锁数值规模。
- 实测（本机 venv，两轮数据吻合）：`9**9**6` 0.07s → `9**9**7` 2.3s，指数每 +1 耗时 ×30；`9**9**8` 分钟级，`9**9**9` 外推约 30 分钟 + 数百 MB。MCP 是 stdio 单线程，一条 `9^9^9=0` 卡死整个 server。
- 放大链（二轮）：错题题面出境给宿主 → 宿主回传 self_check —— 恶意构造的题面可以**间接注入**这条等式，不需要宿主"灵机一动"。
- 修法：改用 float 运算 + `math.isfinite` 上限检查；或对操作数位数在求值前设限；超限按 `undecidable` 处理（不是报错）。

### 19. 包一 CDP 通道没接包二的指纹门禁（二轮新发现，集成缝隙）

- 位置：`browser_collect.py:302-315`（捕获）、`:387`（`json_to_topics` 调用在 try 外）
- `check_response` 只挂在 `zhixue_web` 客户端上（`_get` 里）；CDP 捕获的 getErrorbookList 响应体直接进 `json_to_topics`，全程无指纹比对。
- 后果：字段改名 → KeyError 硬崩；字段**类型**变了（如 beCorrect 从 bool 变 int）→ 静默入库错数据——正是包二要消灭的失败模式，结果自己的新通道绕过了它。
- 修法：捕获后对响应体跑一次 `check_response("cdp-getErrorbookList", ...)`，指纹基线自然落库。

### 20. acceptance.py 的 `ZX_BROWSER_PROFILE` 用 setdefault，隔离可失效（二轮新发现）

- 位置：`tools/acceptance.py:599-615`
- 问题：`os.environ.setdefault("ZX_BROWSER_PROFILE", ...)` —— 若用户 shell **已设**该变量（`config.py:57-61` 明文推荐用它做隔离），setdefault 不生效，K5 段向**真实** profile 写假死 pid 的 marker，随后 `daemon_status()` 读到死 pid 触发 `clear_marker()`，**删掉真实采集守护进程的 marker**。
- 对比：`mcp_e2e.py:45-53` 对 `ZX_CRED_*` 用的是强制赋值，做法正确；acceptance 的 K5 段漏了。
- 修法：改成强制赋值（与 mcp_e2e 对齐）。

### 27. 自动登录的 RC4 复刻与 rc4.js **不一致**（属实性核查推翻一轮结论，二轮新增）

- 位置：`auto_login.py:84-85`（`rc4_hex` 密钥流）、`:181`（登录请求 password 字段）
- 一轮排除项曾断言"RC4 复刻正确、与真实 rc4.js 逐句一致"——**核查不属实**。逐句比对实测：
  - 真实 `static.zhixue.com/tlsysapp/public/401007/login/login/rc4.js`（649 字节全文在手）核心循环是**单重索引**：
    `var a=(h[d]+(h[b]%256))%256; l[e]^h[a]` —— 密钥流 = `S[(S[i]+(S[j]%256))%256]`；
  - `rc4_hex` 是**双重索引**：`k = S[(S[i]+(S[j]%256))%256]`（`:84`）然后 `^ S[k]`（`:85`）—— 密钥流 = `S[S[...]]`，比 JS 多套一层 S[]；
  - 数值实验：同一明文/密钥（`13800138000` / `zxlogin_secret`）两种逻辑输出**不同**；
  - git 历史（`git log -S`）：双重索引自初始提交 `9e69f1d` 就存在——从未与 rc4.js 一致过。
- 后果推论：登录请求 `password=rc4_hex(password)` 发出的密文与真实前端不同；若服务端按 rc4.js 解密，**自动登录从写下起就不可能成功**（真机曾收到的"账号或密码错误"与加密错误时报错相同，无法区分——一轮审计自己也指出了这一点，但它的源码比对结论错了）。
- 影响面：只影响账密自动重登（`ensure_session` → `auto_login`）；Cookie 通道 `zx_session_set` 与 CDP 通道不受影响。
- 修法：`rc4_hex` 密钥流改单重（`out.append(chr(ord(ch) ^ S[a]))`，去掉 `k = S[...]` 中间层），再用真机账号验证一次登录。

## P1/P2 · 数据完整性（跨通道一致性）

### 6. 指纹把近似日期算进身份，且两条通道时区口径不一

- 位置：`models.py:213-220`（指纹 basis）；`zhixuewang.py:189`（UTC）；`fetch_homework.py:188`（本地时间）；`browser_collect.py:394`（None）
- 问题：同一份卷子跨通道同步时日期差一天/缺失 → 指纹不同 → **重复入库**，直接违背 `fingerprint()` 注释里"同一道题从 API 和导出各拿一次应合并成一条"的承诺。
- 顺带：`stem[:800] / standard[:400]` 截断让超长题有碰撞可能（低概率，但指纹是身份，建议哈希全文）。
- 修法：指纹剔除 date（它本来就近似）或统一为本地日期；去掉截断。

### 7. CDP 通道的 subject 是试卷名，联调前必须修

- 位置：`browser_collect.py:362`（`subject_name=each["paperName"]`）、`:400`（拿它当题目学科入库）
- 后果：错题本的学科字段被"20260918八年级数学午练"这类试卷名污染，`zx_subjects` 会把它们当科目列出来；叠加 exam_date=None（见 #6），CDP 与通道 B 对同一批题**必然**双份且学科错误。
- 根因：通道 B 的学科来自 `get_subjects`（`zhixuewang.py:423-447`），CDP 通道缺了这一环的等价物。

### 8. sync_log 的口径失真（二轮修正并扩充）

- 位置：`zhixuewang.py:467`
- 问题：`log_sync_end(added=entry["count"])` 记的是**抓到的题数**不是新增数（真实 added 在 report 里），且 `failed=0` 写死——即使该科有入库失败。
- 【二轮修正】一轮说"browser_collect.sync_captured:415 记对了"——只对了一半：sync_captured 的 added/updated 口径正确，但 `log_sync_end(error=...)` 用的是**全局** `report["errors"]` 而非本试卷组的错误（`browser_collect.py:415-417`）：多份试卷时，第一份卷子的日志会背上后面卷子的错误，`zx_sync_log` 审计数据失真。两处口径各有毛病，都得修。

## 安装链路与 web / promo-video（子代理审计，含实测证据）

### P1

- **GBK 管道崩溃**：`install.py:178,199`、`tools/setup_account.py:53` 输出 `⚠`/`✓`。中文 Windows 下**管道输出**默认 cp936（U+26A0 无法编码，实测）——AI 助手跑安装器恰恰是管道捕获；崩溃点在 pip 装完之后、MCP 配置之前，时机最差。
  修法：入口加 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`（stderr 同理），或 install.ps1 设 `PYTHONUTF8=1`，或换成 `[!]/[OK]`。建议全做。
- **密码走命令行**：web 提示词（`web/src/installPrompt.js:4`）引导用户把真实密码填进 `--password` 参数发给 AI——PSReadLine 明文历史 + argv 进程可见 + 密码先出本机到模型供应商。
  修法：提示词改为指路 `tools/setup_account.py` 的 getpass 路径（已存在）；或支持 `ZX_PASSWORD`/stdin 传入。
