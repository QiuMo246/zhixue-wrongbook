## 1. ⚠️ 重要缺陷：`login_cookie` 的字符串解析很脆

**源码** `zhixuewang/account.py:47-59`

```python
def login_cookie(cookies: Union[dict, str]) -> Account:
    session = get_basic_session()
    if isinstance(cookies, str):
        cookies = dict(item.split("=") for item in cookies.split("; "))
    session.cookies.update(cookies)
    session.cookies.set("uname", base64.b64encode(cookies["loginUserName"].encode()).decode())
    return session_to_account(session)
```

三个真实风险：

| # | 风险 | 触发条件 | 后果 |
|---|---|---|---|
| 1 | `cookies.split("; ")` 只认「分号+空格」 | 浏览器复制出来的 Cookie 是 `a=1; b=2` 还是 `a=1;b=2` 不确定 | 整串被当成一个键，登录失败 |
| 2 | `dict(item.split("="))` 遇到值里含 `=` 会炸 | Cookie 值常带 base64 padding（`==`） | `ValueError: dictionary update sequence element #N has length 3; 2 is required` |
| 3 | **必须有 `loginUserName` 这个 Cookie** | 少了它就 KeyError | `KeyError: 'loginUserName'` |

**处理方式**：我们的适配器**不把原始字符串交给库**，而是自己稳健地解析成 `dict` 再传进去，
并且提前检查 `loginUserName` 是否存在，给出人话提示。见 `adapters/zhixuewang.py`
的 `parse_cookie_string()`。

> 顺带说：架构文档第 11 节的 P0 验证脚本里写的是
> `zxw = login_cookie("粘贴你的Cookie字符串")`——**照抄这段代码有概率直接报错**。
> 我们已把 `tools/verify_p0.py` 改成先解析再传 dict。

## 3. ❌ 与文档不符的 3 处

### 3.1 `difficulty` 的类型不是 0~1 的浮点，是 `int`

- **文档假设**：`"difficulty": 0.62`（0~1 的浮点，越大越难）
- **实际**：`models.py:469` 写的是 `difficulty: int`，赋值来源是接口的 `difficultyValue`
- **影响**：`check_practice` 的「难度落在 ±0.15 区间」这条**硬约束**在 0~1 刻度上才成立。
  如果平台实际是 1~5 或 0~100 的整数刻度，±0.15 会退化成「必须完全相同」，闸门直接失效。
- **处理方式**（不猜，且不假装闸门有效）：
  1. 新增 `config.yaml` 的 `difficulty.scale` 配置，默认 `unknown`
  2. `QuestionPart` 新增 `difficulty_scale` 字段记录该题难度用的是哪种刻度
  3. `scale=unknown` 时，难度闸门**自动降级为软参考**并给出警告——
     宁可说「这项没校验」，也不拿一个错的阈值假装通过
  4. 拿到真实数据后填上 `assumed_max`（例如 5 或 100），闸门自动恢复为硬约束
- **需要你做的验证**：跑一次 `tools/verify_p0.py`，看 `difficulty` 的实际取值范围

### 3.2 `standard_answer` 的注释写的是「网址」

- **文档假设**：`standard_answer` 是标准答案文本
- **实际**：`models.py:474` 的注释是 `standard_answer: str  # 网址`
- **影响**：如果它真是 URL，直接当答案文本用会得到一串链接，
  错因分析会基于垃圾输入得出结论。
- **处理方式**：适配器检测「是否像 URL」：
  - 像 URL → 记到 `standard_answer_url`，正文改用 `answer_html`（`models.py:464`）
  - 不像 → 正常当文本用
  - 两种情况都在同步报告里标明，让人知道数据实际长什么样

### 3.3 `subject_name` 字段里装的其实是**试卷名**

- **实际**：`student/student.py:846` —— `subject_name=each["paperName"]`
- **影响**：把它当学科名用会得到「XX中学期中考试数学试卷」这类字符串，
  和 `get_subjects()` 返回的「数学」对不上，两条数据没法关联。
- **处理方式**：学科名一律以 `get_subjects()` 的 `Subject.name` 为准，
  `ErrorBookTopic.subject_name` 只作为 `paper_name`（试卷名）记录。

## 4. 🔍 重要补充：平台可能**确实有**考点数据（推翻文档一部分前提）

架构文档第 2 节的核心论断是：

> 平台没有给的两样东西：知识点标注、错因分析。**这两个缺口就是我们这个工具的全部价值所在。**

但库的 URL 常量里有这两个接口（`student/urls.py:41-43`）：

```python
GET_LOST_TOPIC_URL   = ".../zhixuebao/report/paper/getExamPointsAndScoringAbility"  # 考点与得分能力
GET_SUBJECT_DIAGNOSIS = ".../zhixuebao/report/exam/getSubjectDiagnosis"             # 学科诊断
```

`getExamPointsAndScoringAbility` 直译是「**考试考点与得分能力**」——
这几乎可以肯定平台内部**有考点（知识点）维度的数据**，只是：

- 库**没有封装**这两个接口（全库搜索，`GET_LOST_TOPIC_URL` 零引用）
- 智学网的网页端报告页大概就是用这两个接口渲染的

**这意味着什么（诚实版）：**

| 原判断 | 修正后 |
|---|---|
| 「知识点标注」是本工具的独有价值 | **不成立**。平台可能有考点数据，只是没被库封装 |
| 「错因分析」是本工具的独有价值 | **仍然成立**。考点 ≠ 错因；「这道题为什么错」平台不做 |
| 我们可以省掉知识点标注 | **不一定**。平台的考点是「这道题考什么」，和我们按 taxonomy 标注是同一件事，**如果平台给得准，我们没必要重复造** |

**处理方式**：
1. 不删掉我们自己的知识点标注链路（它是错因分析的输入，且能覆盖平台不给的场景）
2. 在 `adapters/zhixue_web.py`（通道 C）里**预置**这两个接口的调用骨架，
   标注为「待验证」——拿到真实响应后就能判断要不要用平台数据替代自算
3. 在验收报告里把这条列为**待用户验证的关键假设**

## 5. 其它核实到的实现细节

### 5.1 `get_errorbook` 的第二个参数到底是 paperId 还是 topicSetId？——**不确定**

```python
# student/student.py:822-826
def get_errorbook(self, exam_id, topic_set_id: str) -> List[ErrorBookTopic]:
    r = self._session.get(Url.GET_ERRORBOOK_URL,
        params={"examId": exam_id, "paperId": topic_set_id}, ...)
```

- 形参名叫 `topic_set_id`
- 但请求里发出去的键名是 `paperId`
- 而 `get_subjects()` 返回的 `Subject.id` 来自 `paperId`（`student.py:358`）
- `get_latest_exam()` 返回的 `Subject.id` 来自 **`topicSetId`**（`student.py:248`）

两条路径拿到的 `Subject.id` 来源不同。文档示例走的是 `get_subjects()`（→paperId），
与请求键名一致，**大概率正确，但无法在离线状态下证实**。

**处理方式**：适配器先按 paperId 调；如果返回 `errorCode 40217`
（`暂时未收集到试题信息,无法查看`，见 `student.py:830` 注释），
就用 topicSetId 重试一次，并把「哪个生效了」写进同步报告。这是可验证的降级，不是猜测。

### 5.2 `Exam` 没有日期字段

`models.py:321-336` 的 `Exam` 有 `id / name / status / grade_code / subjects /
clazzs / schools / create_user / create_time / class_rank / grade_rank /
academic_year / is_final`，**没有考试日期**。

`create_time` 来自接口的 `examCreateDateTime`（`student.py:261`），
语义是「考试被创建的时间」，**不严格等于考试日期**。

**处理方式**：用 `create_time` 作为考试日期的近似值，并在数据里
`exam.date_approx = true` 标记出来。掌握度的时间衰减权重会用到这个日期，
所以这个近似必须让人知道。

### 5.3 `get_answer_records()` **没有**学生作答文本

文档第 2 节说「客观题：`AnswerRecordDetail.answer` 是文本学生答案」。
核实结果：`models.py:405-411` 的 `TopicRecord` 只有
`title / score / standard_score / subtopic_records`，**没有 answer 字段**；
`SubTopicRecord`（`models.py:396-401`）只有 `score / marking_records`。

**结论**：**库没有暴露客观题的学生作答文本**。
所以「错因分析必须走多模态」这个判断不仅对主观题成立，**对客观题也成立**
（我们只能拿到对错和得分，拿不到学生选了哪个选项）。

**处理方式**：客观题的错因分析置信度上限相应压低；
`get_original()`（`student.py:428`，返回原卷）留作后续可能的补充通道。

> **2026-09-24 补充（实测订正）**：上面这条只对了一半 ——
> 「**库的字段里**没有客观题作答文本」成立，但「**拿不到**」不成立。
>
> `get_original()` 返回的是原始答题卡的扫描图（正面 / 背面），
> **客观题填涂卡就在上面**。用真实账号实测：把图下载下来放大，
> 能直接读出学生涂了哪个选项（例如物理 1372 第 9 题 = B、第 10 题 = A；
> 物理 d7db 第 8 题 = C、第 10 题 = D），并据此把 4 道客观题的错因
> 从「只能猜」提到了有据可依。
>
> 所以正确的说法是：**客观题作答 = 走 `get_original()` 的答题卡扫描图**，
> 代价是需要人（或视觉模型）看图。`answer_type` 字段可以帮上忙：
> `s01Text` 是客观题（机器阅卷）、`s02Image` 是主观题（人工阅卷），
> 本次 27 题里 111 vs 203 全库范围内 100% 分离。
>
> **对错因分析的影响**：客观题的置信度上限**不必**压低到「只能看对错」，
> 只要愿意走一遍 `get_original()` 就能拿到真实作答。

### 5.4 `login_playwright` 其实**不占** profile

文档第 4 节担心「Playwright 持久化上下文冲突」。核实：

```python
# account.py:66-67
browser = await chromium.launch(headless=False)
context = await browser.new_context()      # ← 非持久化上下文
```

它用的是 `new_context()`，**不是** `launch_persistent_context`，
而且用完 `await browser.close()`。所以：

- **不存在 profile 占用冲突**（文档的这条担忧对库路径不成立）
- 但它仍然会**弹出一个浏览器窗口**，且 `headless=False` 是写死的
- 它填的是 `wap_login.html` 表单（`account.py:71-76`），
  如果智学网改了登录页的 DOM id，这条路会失效

**结论**：`login_cookie` 作为主路径的判断**依然正确**，但理由要改：
不是「避开 profile 冲突」，而是「避开弹窗、避开密码、避开人机验证」。

### 5.5 需要 XToken，且 600 秒刷新一次

`student.py:68-95`：每个请求都要带 `authbizcode / authguid / authtimestamp /
authtoken / XToken` 五个头，其中 `XToken` 由 `/container/app/token/getToken`
签发，缓存 600 秒。库已自动处理，我们不需要重复实现——
但要知道**每次同步至少会产生 1 次额外的 token 请求**，这是抓包时会看到的正常现象。

### 5.6 库会主动抛异常的情况

- `get_errorbook` 在 `errorCode != 0` 时 `raise Exception(data)`（`student.py:831`），
  **抛的是裸 `Exception`**，不是自定义异常类
- `get_latest_exam` / `get_subjects` 等在 `not r.ok` 时抛 `PageConnectionError`
- 所以适配器捕获异常时必须宽：`except Exception`，并按错误码分类给提示

### 7.3 这条发现改变了什么

架构文档第 2 节的原判断是：

> 平台没有给的两样东西：知识点标注、错因分析。**这两个缺口就是我们这个工具的全部价值所在。**

**实测结果：前半句不成立。**

| 原判断 | 实测后的修正 |
|---|---|
| 平台没有知识点标注 | ❌ **错**。平台有考点名 + 权重 + 掌握度（0~100），粒度到具体知识点 |
| 平台没有错因分析 | ✅ **仍然成立**。考点 ≠ 错因；「这道题**为什么**错」平台确实不做 |
| 自建掌握度公式是独有价值 | ❌ 大幅削弱。平台的 `myScoreAbility` 就是同一件事，而且它有平台侧的真实权重 |
| 自建知识点标注是独有价值 | ⚠️ **部分削弱，但没有完全失效** —— 见下 |

**为什么自建标注没有完全失效（要诚实说清）：**

1. 平台的考点是**考试级聚合**（某个考点权重多少、掌握多少），**不直接告诉你「第 18 题对应哪个考点」**。
   要把错题和考点连起来，仍然需要逐题标注。
2. 平台的考点用的是**平台自己的 ID 体系**（`020449000003016n`），
   与 `taxonomy.yaml` 的「学科/章节/知识点」路径**不通用**，两者无法直接映射。
3. 平台的考点名是**细颗粒知识点**（如「含30°角的直角三角形」），
   而本项目的词表是**教材章节级**（如「勾股定理」），粒度不同。

### 7.4 建议（按优先级，供项目作者决策）

1. **把这两个接口正式接进来**（现在只有探测骨架）。
   建议在 `zx_sync` 时顺带拉一次，存进本地库 —— 它是**平台侧的真实数据**，
   比自算的掌握度更可信，而且能作为交叉校验源。
2. **重新表述价值定位**：从「平台不做的我们做」改为
   「平台做**聚合统计**，我们做**逐题归因**」——
   逐题错因 + 逐题考点归属 + 同类题生成，这三件平台确实不做。
3. **`taxonomy.yaml` 与平台考点做一次映射**（可选，工作量不小）：
   如果能把平台考点 ID 映射到本地词表，就能同时拿到
   「平台的真实权重/掌握度」和「本地的可读路径」。至少可以先做一层
   「平台考点名 → 本地知识点」的别名表。
4. **`zx_profile` 增加一个「与平台掌握度对比」的输出**：
   同一批题，自算掌握度 vs 平台 `myScoreAbility`，差异大的知识点值得人工看一眼。
   这是低成本、高信息量的一步。
